## 首屏改为双主题自动轮播

需求：首屏美照改成多张轮播，浅色模式读 `1.jpeg`~`10.jpeg`，深色模式读 `11.jpeg`~`20.jpeg`，各最多 10 张，每 2s 切一张循环播放，动画要丝滑流畅。

实现（`src/App.vue` + `src/style.css`）：
- 常量 `heroSlidesLight` / `heroSlidesDark` 各列 10 个路径（替代原 `heroPhoto` 单图）。新增 `HERO_SLIDE_INTERVAL = 2000`。
- 计算属性 `heroSlides`（按 `theme` 选组）、`heroSlideCount`、`heroHasPhoto`、`heroCanAutoplay`；`heroSlideItems` 只保留 current/next 两项。
- **关键性能设计**：`heroSlideState(index)` 用环形差值 `((i - active) % n + n) % n` 判定 current(0)/next(1)/hidden，模板 v-for 只渲染 current + next 两层，避免 10 张 2400px 大图同时进合成层。已用独立脚本验证 count=2/3/10 循环切换全程恒为「1 current + 1 next」。
- 动画：纯 CSS 交叉溶解。`.hero-photo--current`（z-index 2, opacity 1, scale 1）↔ `.hero-photo--next`（z-index 1, opacity 0, scale 1.045），1.05s cubic-bezier(.4,0,.2,1)，next 的 transform 用 1.4s 缓出产生轻微推镜感；加 `will-change: opacity, transform` + `backface-visibility: hidden`。**没用任何 JS 逐帧动画。**
- 暂停条件复用画廊那套：hover / 键盘聚焦 / 页面不可见 / prefers-reduced-motion。hero 容器加 `mouseenter`/`mouseleave`/`focusin`/`focusout`，新增 `heroObserver`（IntersectionObserver）。`onBeforeUnmount` 清理 `heroTimer` 与 `heroObserver`。
- `watch(theme)` 切主题时把 `activeHeroSlide` 归零，避免索引越界。
- 曾误留未使用的 `currentHeroSlide` 计算属性导致 `vue-tsc` 报 TS6133，已删除——**本项目 build 启用了 noUnusedLocals，新增变量务必确认被引用。**

约定：文件名纯数字不补零（`1.jpeg` 而非 `01.jpeg`）；只放实际张数即可，无需改代码；两组张数可不同。

验证：`npm run build` 通过；轮播状态机逻辑单独脚本校验通过。本机 bash 已坏（coreutils 缺失），验证脚本用 PowerShell 调 managed node 跑。

## ⚠️ 事故与回滚：我把画廊堆叠轮播改坏了

用户指出「留一块位置，给你镜头里的暖暖」模块原有的堆叠图自动轮播被我改掉了。

**我的错误**：上一轮做「有几张播几张」时，我把画廊的卡片数从固定 5 改成了 `gallerySlideCount = Math.max(实际探测张数, 1)`。而当时目录里**一张 gallery 照片都没有**，探测结果为 0，于是 `gallerySlideCount = 1` → 只渲染 1 张 card → 堆叠转场与自动轮播彻底消失。

**根因**：我把「首屏按实际张数播」这个需求错误地推广到了画廊，还顺手把 `galleryCanAutoplay` 加上 `galleryPhotoCount > 1` 的门槛，零照片时连定时器都不启。原设计是**固定 5 张叠放卡片**，卡片数本就与照片数量无关。

**回滚做法**（对照 `git show HEAD:src/App.vue` 逐项核对）：
- `const gallerySlideCount = GALLERY_SLIDE_LIMIT`（常量 5，非 computed）—— 这是关键。
- `galleryOffset` / `galleryCardLayer` / `setGallerySlide` 全部改回常量运算（去掉 `.value`）。
- `galleryCanAutoplay` 去掉 `galleryPhotoCount > 1`，恢复原条件。
- `galleryPhotoCount` 与 `galleryPhotos` computed 因不再被使用而删除（noUnusedLocals 会报错）。
- 画廊探测改为**5 个卡位并行独立探测**（不再「遇缺即停」），因为卡位固定，缺哪张只让那张显示占位骨架；`galleryAvailable[slot]` → 卡片加 `has-photo` 类 + 渲染对应 `<img>`。
- 用 `git diff HEAD -- src/App.vue` 逐行核对，确认剩余差异只是把字面量 `5` 换成等值常量 + 新增 `:class="{ has-photo }"`，行为与原版一致。

**教训**：
1. **改视觉/动效组件前先确认它是「装饰性固定结构」还是「数据驱动列表」。** 堆叠卡片属于前者，卡片数不该跟数据量耦合。
2. **不要把某个模块的需求顺延到相邻模块。** 用户说「首屏有几张播几张」，画廊没被提及就不该动。
3. 改公共函数（当时 `gallerySlideCount` 被画廊多处引用）要评估连带影响，必要时 `git show HEAD:<file>` 做原始比对。

画廊卡位缺号是允许的（独立探测）；只有**首屏**因为依赖连续前缀，才要求文件名连号。

## 首屏版式：照片右偏 + 文字卡片左偏，两者部分重叠

需求：`.hero-copy` 不再压在照片正上方居中，`.hero-art` 不居中、整体右移，`.hero-copy` 左移，形成卡片右半部叠压照片左边缘的错位构图。**明确只改桌面端，移动端保持原竖向堆叠。**

实现（纯 CSS，`src/style.css`，HTML 未动——`.hero-copy` 本来就是 `.hero-art` 的兄弟节点，靠绝对定位叠上去的）：
- `.hero-section` 新增两个局部变量：
  - `--hero-gutter: max(48px, calc((100vw - 1200px) / 2))` —— 桌面端左基准边距，统一了原先散落在 `.hero-art` / `.hero-copy` / `.hero-index` 里的同一表达式。
  - `--hero-overlap: clamp(56px, 6vw, 96px)` —— 卡片比照片左边缘再往左多出的重叠量。
- `.hero-art`：`margin-inline: auto` → `margin-left: calc(var(--hero-gutter) + var(--hero-overlap)); margin-right: var(--hero-gutter);`（右偏 + 右侧贴基准边距）；`width` 改 `min(var(--content-width), calc(100% - var(--hero-gutter)))` 让右侧留白仍等于 gutter。
- `.hero-copy`：`left` 从 `max(48px, ...)` 改为 `var(--hero-gutter)`（左移 = gutter 而非 gutter+overlap —— 更简单且重叠量靠照片左移来产生）；`width` 上限 600px → 620px，可用宽度扣除 `--hero-gutter`。
- 响应式复位（保证移动端不受影响）：
  - `@media (max-width: 1100px)`：只把 `--hero-gutter` 调到 `40px`、`--hero-overlap` 微缩，重叠效果保留（避免负 margin 风险）。
  - `@media (max-width: 900px)`：`--hero-overlap: 0px`，`.hero-art` 恢复 `margin-inline: auto`，`.hero-copy` 恢复 `left: 40px` —— 即回到原版式。
  - `@media (max-width: 640px)`：`--hero-gutter: 0px; --hero-overlap: 0px`，`.hero-art` 本来就是 `width: 100%`。
- 重叠量调参入口就是 `--hero-overlap`（桌面）/ 1100 断点里的那行。

**桌面端最大断点是 1100px（不是 1200px）**，`.hero-section` 的 `padding-inline` 为 0，靠子元素 margin 撑边距。

验证：`vite build` 通过（dist 正常产出）。

### 补充：卡片水平位置改用独立偏移量 `--hero-copy-shift`

用户反馈「按你说的在 `left` 里减去任何数，卡片就贴到左边」。**根因**：`--hero-gutter: max(48px, calc((100vw - 1200px) / 2))` 在视口 <1200px 时第二项为负，`max()` 恒取 `48px`，所以减任何数都是在 48 上做减法，很快变负 → 负 `left` 把卡片推出视口左边界（视觉上像"贴左"，实为被裁）。

修复：`.hero-section` 新增 `--hero-copy-shift: 0px`；`.hero-copy` 的 `left` / `width` 都基于它叠加 —— `left: calc(var(--hero-gutter) + var(--hero-copy-shift))`、`width: min(620px, calc(100% - var(--hero-gutter) - var(--hero-copy-shift) - 48px))`。这样调卡片不会牵动照片/页码（`--hero-gutter` 三处共用）。

**教训**：给用户"调参指引"前先确认该变量在当前生效区间内的**实际取值行为**（尤其 `max()`/`clamp()`/`min()` 的退化分支），不要只看表达式形式就给出"加/减都可以"的建议。面向用户的调参项应尽量做成**独立且语义单一**的变量。

### 再改：用户要求撤销 `--hero-copy-shift`，改用内联展开

用户不想为卡片位移单开变量。评估过的替代方案及结论：
- **A 写死 `left: 120px`** —— 可行但大屏失去响应式，重叠关系随窗口漂移；`width` 也要同步改。
- **B `.hero-section { padding-left }` + 卡片回正常流** —— 会把照片一起推走，与"只挪卡片"冲突，否决。
- **C `transform: translateX()`** —— **实测有坑，否决**：`motion-v` 通过**内联 style** 写 `transform`（`heroVariants` 用 `y` 做纵向入场），内联优先级高于样式表，CSS 里的 `translateX` 会在动画期间被覆盖，不可靠。
- **D 内联展开（最终采用）** —— `.hero-copy` 的 `left` / `width` 直接内联 `max(48px, (100vw - 1200px) / 2)` 表达式。

最终状态：
- `.hero-section`: 回到只有 `--hero-gutter` + `--hero-overlap`（`--hero-copy-shift` 已删）。
- `.hero-copy`(L122): `left: calc(max(48px, (100vw - 1200px) / 2) + 40px)`；`width: min(620px, calc(100% - max(48px, (100vw - 1200px) / 2) - 88px))`。**两处表达式必须同步改**，偏移量 `+40px` / `-88px` 是一对（40 卡片偏移 + 48 右侧留白）。
- **连带修复**：`@media 1100px` 原先只覆盖 `--hero-gutter: 40px`，卡片 `left` 内联后该覆盖失效（卡片会跳到 48px）。已在该断点给 `.hero-copy` 显式写 `left: 52px; width: calc(100% - 92px)`。
- 900px / 640px / 380px 断点本就有显式 `left` 覆盖，不受影响。

**新增教训**：把 `left` 从 `var(--x)` 改成内联表达式，会让此前依赖该变量的断点覆盖**静默失效** —— 这类"变量引用改内联"的重构必须把所有断点里的覆盖逐条排查。另：确认 `motion-v` 元素不要用 CSS `transform` 做静态位移，会被内联 style 覆盖。

## 方案 C：滚动条起点改到 .site-header 下端（已实施，后按用户要求回退）

> ⚠️ **本节描述的实现已被回退，当前代码不包含方案 C。** 保留记录以供参考（含本机 Playwright 验证环境备忘）。回退详情见本节末尾。

需求：让最右侧滚动条不要从视口顶端开始，改从 `.site-header` 底边开始。

**评估过程**：根滚动条无法用 CSS 控制起点，试过并否决：
- `::-webkit-scrollbar-button:vertical:start` 撑高度 —— 只有 WebKit 生效，Firefox 无效。
- `overflow: hidden` —— 禁用整页滚动，不可用。
- **最终选方案 C：把整页滚动交给容器**。

**实施（`src/App.vue` + `src/style.css`）**：

模板结构（`App.vue`）：
```
<div class="site-shell">
  <a class="skip-link">        ← 留在外层（fixed）
  <motion.div class="reading-progress">  ← 留在外层（fixed）
  <div ref="pageScrollEl" class="page-scroll">   ← 新增滚动容器
    <header class="site-header">
    <main>
    <footer>
  </div>
  <Transition> lightbox          ← 留在外层（fixed 遮罩）
</div>
```

## 画廊：手动切图后自动播放应停止

需求：「留一块位置，给你镜头里的暖暖」模块里，用户点了手动左右切换按钮后，图片就不该再自动切换。

**实现**：新增「用户手动操作」专用的入口，切图后顺手关闭自动播放标记。

- `setGallerySlideByUser(index)` —— 调 `setGallerySlide()` 后把 `galleryAutoplayRequested` 置 `false`。
- `showNextGallerySlideByUser()` / `showPreviousGallerySlideByUser()` —— 包装函数，供箭头与方向键用。
- 定时器**仍走原 `showNextGallerySlide()`**（不经过 ByUser 版本），所以自动播放不会被自己关掉。这一点很关键：两条路径必须分开，否则自动播放跑一张就自我暂停。
- 模板三处改绑：左箭头 → `showPreviousGallerySlideByUser`、右箭头 → `showNextGallerySlideByUser`、小圆点 → `setGallerySlideByUser(slot - 1)`；`handleGalleryKeydown` 里方向键也换成 ByUser 版本。
- 副作用清理：`showPreviousGallerySlide` 因不再被引用，触发 `noUnusedLocals` TS6133，**已删除**（`showNextGallerySlide` 仍被定时器使用，保留）。

**过程中发现并修掉的两个既有 Bug**（都不是本次需求引入，但会直接让「点播放按钮恢复」失效，必须一起修）：

1. **聚焦暂停把播放按钮自己拦住了**。原 `galleryCanAutoplay` 含 `!galleryFocused`，而点任何控件都会触发 `@focusin` 把 `galleryFocused` 置 `true`；点播放按钮后焦点仍留在轮播内，`focusout` 不触发 → 条件恒假 → 定时器永不启动。现象是「aria-pressed 变 true，但画面不动」。
   **修法**：删掉画廊的聚焦暂停（`galleryFocused` ref、`handleGalleryFocusOut`、模板上的 `@focusin`/`@focusout`）。这与首屏轮播此前的处理一致（用户当时明确要求首屏去掉聚焦暂停）。
2. **悬停暂停同样会拦住播放按钮**。鼠标停在控制条上点「播放」，因为指针仍在 `.gallery-carousel` 内，`galleryHovered` 为 `true`，条件仍为假。

## `.gallery-photo` 圆角 18px + 堆叠效果宽窄屏差异的成因

需求：① `.gallery-photo` 圆角改 18px；② 排查「宽屏堆叠效果不明显、窄屏明显」的原因。

### ① 圆角

`src/style.css` L297：`.gallery-photo` 加 `border-radius: 18px`，只改这一行。

注意该图片是 `position: absolute; inset: 0` 铺满 `.gallery-card`，而卡片自身已有 `border-radius: 8px` + `overflow` 未裁剪（`.art-placeholder` 才是 `overflow: hidden`）。**两者圆角不相等会造成「图片圆角比卡片圆角大、四角露出卡片底色」**。图片 18px > 卡片 8px，因此四角会露一点卡片背景。若要完全贴合，应把 `.gallery-card` 的圆角也提到 18px —— **本次按用户要求只改了 `.gallery-photo`，此点已告知。**

### ② 宽窄屏差异的根因：偏移量是**固定 px**，而卡片尺寸随视口缩小

堆叠位移写在 `App.vue` 的 `galleryCardMotion()`：
```ts
x: offset * 12,       // 每层 +12px
y: offset * 9,        // 每层 +9px
scale: 1 - offset * 0.04,   // 每层 -4%
opacity: 1 - offset * 0.12  // 每层 -12%
```
`x` / `y` 是**固定像素**，不随卡片大小缩放；只有 `scale` 是比例。于是「堆叠可见度」= 位移量 ÷ 卡片宽度，屏幕越窄卡片越小、比值越大，堆叠越明显。

**实测数据（Playwright 真实渲染，`.art-gallery` 容器与第 5 层卡片的 translate）**：

| 视口宽 | 容器宽 | 每层 X 位移 | 位移占卡片宽 | 观感 |
|---|---|---|---|---|
| 1440 | 648.6 | 12px | 1.85% | 几乎看不出 |
| 1280 | 632.8 | 12px | 1.90% | 几乎看不出 |
| 1100 | 554.7 | 12px | 2.16% | 很弱 |
| 900 | 680 ⚠️ | 12px | 1.76% | 很弱 |
| 700 | 626 | 12px | 1.92% | 很弱 |
| 560 | 488 | 12px | 2.46% | 较明显 |
| 420 | 348 | 12px | **3.45%** | 明显 |

**关键点**：% 越小越看不出，420px 时是 1440px 时的近 **1.9 倍**相对位移 → 这就是「窄屏明显」的直接原因。

**还有一个反直觉之处**：900px 视口反而比 1100px 更不明显（容器 680 > 554.7）。因为 `@media (max-width: 900px)` 里 `.art-gallery { width: min(100%, 680px); margin-inline: auto }` —— 这个断点把画廊**从「跟随栅格列宽」切换成「固定最大 680px 居中」**，导致 900px 处的容器反而变宽。所以宽窄屏差异不是单调的，在 900px 附近有个凸起。

**可选的改进方向**（已告知用户，未改）：
- 把 `x` / `y` 改成随容器宽度变化的量（如用 CSS 变量 + `clamp()`，或 JS 里按 `.art-gallery` 的 `offsetWidth` 取百分比），让位移占比在全屏宽区间恒定。
- 或直接加大位移绝对值（如 `x: offset * 20`），但会牺牲窄屏观感（窄屏会显得散）。
- 或让 `scale` 承担更多视觉差（现在每层仅 -4%，5 层累计 0.84，差异偏小）。

**验证**：`vue-tsc --noEmit` 通过；`vite build` 通过（`index-B83_u7ps.css` / `index-Bc9-LjTi.js`）。

### 后续：`.gallery-card` 同步提到 18px（用户确认「要一起改」）

只改 `.gallery-photo` 会导致图片圆角（18px）> 卡片圆角（8px），图片四角比卡片多裁进去一点，**露出一丝卡片底色**。用户要求一起改，故 `.gallery-card` 的 `border-radius` 也从 `8px` → **`18px`**。

**确认无断点覆盖**（这是保证两端始终相等的关键）：grep 过整份 `style.css` ——

- `.gallery-photo` 圆角只在 L297 定义一次；

所以两端在所有屏幕尺寸下自动保持相等，无需在断点里同步维护。

## 画廊堆叠效果均一化（方向 1 实施）

需求：解决「宽屏堆叠不明显、窄屏明显」，让各屏幕宽度下堆叠观感一致。

**用户确认的三个口径**（用 AskUserQuestion）：
- 强度：**偏强，位移步长 ≈ 容器宽 3.2%**
- **接受全屏宽统一**（窄屏会从 3.45% 收敛到统一档位，略变弱）
- **位移 + scale 一起调**

**根因回顾**：`x` / `y` 是**固定像素**（12px / 9px），而卡片尺寸随视口缩小 → 位移占比 = 12px ÷ 卡片宽，屏幕越窄占比越大。

**实现（`src/App.vue`）**：

1. 新增 `artGalleryWidth` ref + 模块级 `artGalleryEl`：
   ```ts
   const artGalleryWidth = ref(0)
   function setArtGalleryEl(instance: unknown): void {
     artGalleryEl = getMotionElement<HTMLDivElement>(instance)
     syncArtGalleryWidth()
   }
   let artGalleryEl: HTMLElement | null = null
   function syncArtGalleryWidth(): void {
     const width = artGalleryEl?.offsetWidth ?? 0
     if (width) artGalleryWidth.value = width
   }
   ```
2. 步长计算，**带上下限**：
   ```ts
   const galleryStackStep = computed(() => {
     const width = artGalleryWidth.value
     if (!width) return 12
     return Math.min(30, Math.max(12, width * 0.032))
   })
   ```
   **上下限是必须的**：400px 以下容器宽 × 3.2% 会小于 12px，导致窄屏反而看不出堆叠；30px 上限则兜住 900px 断点处容器宽度跳变（那里 `.art-gallery` 从「栅格列宽」切成「固定 680px 居中」，容器反而变宽）。
3. `galleryCardMotion()` 改用步长，并加大 scale / opacity 层次：
   ```ts
   function galleryCardMotion(slot: number): Record<string, number> {
     const offset = galleryOffset(slot)
     const step = galleryStackStep.value
     return {
       x: offset * step,
       y: offset * step * 0.75,   // 保持原来的 12:9 = 4:3 比例
       scale: 1 - offset * 0.06,  // 原 0.04
       opacity: 1 - offset * 0.14 // 原 0.12
     }
   }
   ```
   `y` 用 `step * 0.75` 是**刻意保持原 12:9 的斜率关系**（9/12 = 0.75），只改步长不改方向比例。
4. 新增 `ResizeObserver` 跟踪容器尺寸，窗口缩放/断点切换时同步：
   ```ts
   const artGalleryObserver = new ResizeObserver(() => { syncArtGalleryWidth() })
   onMounted(() => { ... artGalleryObserver.observe(artGalleryEl) })
   onBeforeUnmount(() => { ... artGalleryObserver.disconnect() })
   ```
   模板：`<div :ref="setArtGalleryEl" class="art-gallery" aria-live="off">`。

| 视口 | 容器宽 | stepX | **位移占比** | scale 序列 | 最低 opacity |
|---|---|---|---|---|---|
| 1440 | 648.6 | 20.77 | **3.20%** | 1/.94/.88/.82/.76 | 0.44 |
| 1280 | 632.8 | 20.26 | **3.20%** | 同上 | 0.44 |
| 1100 | 554.7 | 17.76 | **3.20%** | 同上 | 0.44 |
| 900 | 680 | 21.76 | **3.20%** | 同上 | 0.44 |
| 700 | 626 | 20.03 | **3.20%** | 同上 | 0.44 |
| 560 | 488 | 15.62 | **3.20%** | 同上 | 0.44 |
| 420 | 348 | 12 | 3.45% | 同上 | 0.44 |

**6 / 7 个视口精确落在 3.2%**，只有 420px 因触到 12px 下限而为 3.45%（这是预期的下限保护，非缺陷）。对比改造前：1440px 是 1.85%、420px 是 3.45%，**差近 1.9 倍；现在基本拉平**。

scale 层次从「每层 -4%（累计 0.84）」加大到「每层 -6%（累计 0.76）」，opacity 从 -12% 到 -14%，层次感明显增强。截图确认宽屏能清楚看到右侧与底部的层叠边缘。

`vue-tsc --noEmit` 通过；`vite build` 通过（`index-kT6RnuWx.css` / `index-CSyDGIHf.js`）。

**经验**：
1. **「绝对 px 位移 + 相对 scale」混用会让视觉效果随容器尺寸漂移**。凡是「多元素按层偏移」的效果，位移应当与容器尺寸挂钩（百分比 / `em` / CSS 变量），只把「方向比例」写死（本例 `y/x = 0.75`）。
2. 用百分比后**务必加 `min()` / `max()` 上下限**：小屏防止位移退化成看不见，大屏防止断点处容器尺寸跳变导致的突兀放大。
3. 用 `ResizeObserver` 而不是监听 `window.resize` —— 后者在容器因布局变化（非窗口变化）而改尺寸时不会触发。

## 🔴 深色组首屏一张都不播（key 读写不一致）

function heroSlotKey(index: number, group: Theme = theme.value): number { return heroSlotBase(group) + index }

- `probeHeroSlides`：`const base = heroSlotBase(group)`（**原来写的是局部 `group === 'dark' ? 11 : 1`，必须改掉**，否则读写还会再漂移）

## 诊断：`.hero-index` 为什么「往下滑才浮现」

用户问这算不算 bug。**先查代码再回答**，结论：**不算 bug，是定位设计导致的**，但有一个真实的实现缺陷。

**`.hero-index` 本体（`App.vue` L801）**：
```html
<div class="hero-index" aria-hidden="true"><span>01</span><i></i><span>07</span></div>
```
它是 `.hero-section` 的**直接子元素**，**没有任何动画绑定**（不是 `motion.div`，没有 `:initial` / `:while-in-view`）。已用 Playwright 实测：`opacity: 1`、`transform: none`、`display: flex` —— **不存在渐显动画**。所以「浮现」感不是动画造成的。

**它是 `.hero-section` 的 `position: absolute` 子元素，锚在区域底部**：
```css
.hero-index { position: absolute; right: max(48px, calc((100vw - 1200px) / 2)); bottom: 22px; }
```
而 `.hero-section` 的高度**由 `.hero-art` 撑开**（`min-height: 540px` + `aspect-ratio: 16/9` + `max-height: calc(100svh - header - 52px)`）。所以「看得到看不到」= 「首屏区域内高度是否超出视口」。

**实测 11 组视口尺寸**：

| 视口 | section 高 | index.top | 视口高 | 首屏可见？ |
|---|---|---|---|---|
| 1600 x 900 | 689 | 723 | 900 | ✅ |
| 1440 x 900 | 689 | 723 | 900 | ✅ |
| 1440 x 700 | 590 | 624 | 700 | ✅ |
| 1366 x 640 | 554 | 588 | 640 | ✅ |
| 1280 x 620 | 554 | 588 | 620 | ✅ |
| 1056 x 640 | 554 | 588 | 640 | ✅ |
| 900 x 700 | 614 | 642 | 700 | ✅ |
| **640 x 700** | 730 | **767** | 700 | ❌ **需下滚 87px** |
| **420 x 700** | 730 | **767** | 700 | ❌ **需下滚 87px** |

**结论：桌面端（≥900px）本来就可见，不是问题。只有 ≤640px 移动端会掉到首屏之外** —— 因为那里 `.hero-art { min-height: 720px; aspect-ratio: auto; max-height: none }`，区域被拉高到 730px 固定值，而 index 锚在它底部 767px 处。

**🔴 但顺手发现一个真实缺陷（桌面端）**：`.hero-index` 的 `z-index` 未设置，而 `.hero-copy` 是 `z-index: 2`、`.hero-art` 未设 z-index。实测 1440x900 截图中，`01 —— 07` 被 `.hero-art` 的白色圆角矩形**盖住/压边**，视觉上像被裁掉了一部分（图片区域延伸到 x≈1056，index 恰好在它下缘）。这就是用户觉得「没出现 → 滑一下才看到」的真实观感来源之一：**它不是渐显，而是被压在照片下缘、对比度不足**。

## 首屏序号 `01 —— 07` 改为动态

原先是模板里硬编码的两个字符串（`App.vue` 里 `<span>01</span>...<span>07</span>`），与实际张数（浅色 8 / 深色 9）对不上。

**改法（两处，都在 `src/App.vue`）**：

1. 新增两个 computed（插在 `heroHasPhoto` 之后）：
   ```ts
   const heroIndexCurrent = computed(() => {
     const count = heroSlideCount.value
     if (!count) return '01'
     return String((activeHeroSlide.value % count) + 1).padStart(2, '0')
   })
   const heroIndexTotal = computed(() => String(heroSlideCount.value).padStart(2, '0'))
   ```
   - 左边 = **当前正在展示的那张**（`activeHeroSlide` 是 0 基，+1 后补零）→ 会随轮播实时变化，从「静态装饰」变成「进度指示」。
   - 右边 = **当前主题组探测到的实际张数** → 浅色 8、深色 9 自动不同。
   - `% count` 是**防御性取模**：探测可能晚于首帧完成、切主题时索引归零，极端时序下 `activeHeroSlide` 可能短暂超出新张数。

2. 模板加 `v-if="heroHasPhoto"`：
   ```html
   <div v-if="heroHasPhoto" class="hero-index" aria-hidden="true"><span>{{ heroIndexCurrent }}</span><i></i><span>{{ heroIndexTotal }}</span></div>
   ```
   **必须加**：探测完成前 `heroSlideCount` 是 0，不加会先闪一下 `01 —— 00`。

3. **保留 `aria-hidden="true"`**：数字每 3 秒变一次，读屏软件会被持续打断。它仍应是纯装饰 —— 要读屏可读得另做 `aria-live="off"` + 隐藏文案的设计，本次没做。

**验证（Playwright，真实渲染）**：

| 项 | 结果 |
|---|---|
| 浅色总张数 | `01 —— `**`08`** ✅（实际 1~8 存在，9/10 缺） |
| 深色总张数 | `01 —— `**`09`** ✅（实际 11~19 存在，20 缺） |
| 左侧序号随轮播推进 | 浅色采到 `02 03 04 05 06`；深色采到 `01 02 03 04` ✅（每档约 6×500ms ≈ 3s，与 `HERO_SLIDE_INTERVAL` 一致） |
| 640px 移动端 | `display: none` 仍生效 ✅ |

`vue-tsc --noEmit` 通过；`vite build` 通过（`index-CcfQZCXd.css` 未变 —— 本轮没动 CSS / `index-l5u1yTu7.js`）。

**教训（自摆乌龙）**：第一版断言写的是「静止时左侧应为 `01`」—— **错了**。首屏是自动轮播的，读到 `02` 是正常行为。写轮播相关的断言时，**不要把「某个固定值」当成期望**，应断言「值落在合法区间内」+「随时间发生变化」。**这类断言错误会伪装成产品 bug，浪费一轮排查。**

### 🔴 顺带查明：这个过渡**不是**交叉溶解，而是「单层渐显」

用 Web Animations API 把过渡定格在 0ms / 225ms 截图，发现：

- **DOM 里始终只有 2 层**（`current` + `next`），切走的图**立即从 DOM 移除**（`heroSlideItems` 里 `filter(state !== 'hidden')`）。
- 所以过渡过程是：旧图瞬间消失 → 新图从 `opacity: 0` 渐显。**底下没有旧图垫着，露出的是容器底色**。
- 定格 0ms 的截图：浅色下整块图区是米白、深色下是深紫 —— **一张图都没有**。
- 定格 225ms：`current`（新图）`opacity: 0.78`、`next`（下下张）`opacity: 0`。

**因此 CSS 注释「当前图同时淡出……形成无缝交叉溶解」与实现不符**，是旧版遗留的过时注释。实际观感是「整幅图变淡再恢复」（浅色下发白、深色下发灰），而不是两图叠加。

**这是既有的性能取舍**（只挂 2 层以减少合成层），**不是本次改动引入的**，用户也没反馈过异常。若要真正的交叉溶解，需要让退场的那张多留一层并给它加 `transition`（DOM 从 2 层变 3 层）。**已告知用户，未改。**

### 可复用的两个技巧

1. **用 Web Animations API 定格过渡中间帧**（比连拍截图精确）：
   ```js
   document.getAnimations()
     .filter(a => a.playState === 'running' && a.effect.target.classList.contains('hero-photo'))
     .forEach(a => { a.pause(); a.currentTime = ms })   // 先 pause 再 seek 才生效
   ```
   配合 `page.screenshot({ clip: boundingBox })` 可截到任意百分点的中间态。
2. **`getComputedStyle().getPropertyValue('--x')` 返回的是序列化值，会去掉前导零**（`0.45s` → `.45s`）。断言别用字符串相等，**用 `parseFloat` 比数值** —— 我第一版就因此收获了一次假 FAIL。
